# 세션 병합(merge) 감사 기록

10월 2주차 3번 작업 산출물. `08_session_merge.py`가 적용한 병합 규칙을
예측 오차(MAE/RMSE)와 **별개로** 검증한다. 산출 파일은 모두
`docs/merge_audit/`에 있다 (전부 git에 커밋되어 누구나 재현/열람 가능).

## 1. 병합 임계값은 사전에 고정, MAE로 조정하지 않음 (중요)

병합 규칙(시간 간격 ≤180초, GPS 종료~시작 거리 ≤200m, 암시 속도 ≤3m/s,
셋 다 만족해야 병합)은 **10월 1주차(`08_session_merge.py` 최초 작성 시)에
사전에 정한 값**이며, 이후 어떤 단계에서도 baseline MAE/RMSE를 보고
이 값을 바꾼 적이 없다. 이번 2주차 감사(`13_merge_audit.py`,
`15_merge_abc_breakdown.py`)에서도 이 값을 그대로 재사용했을 뿐, 조정하지
않았다. 임계값을 바꿔보는 민감도 분석은 지금 하지 않았고, 하게 되더라도
별도 실험으로만 수행하며 기본값 선택에는 쓰지 않는다 (CLAUDE.md 규칙).

## 2. 병합 대응표 / 체인 길이 분포 (`13_merge_audit.py` 산출)

- `docs/merge_audit/merge_correspondence_table.csv`: 병합된 세션
  (`merged_count > 1`) 4,109개 각각에 대해 `merged_session_id`(병합 결과의
  대표 id, 체인의 첫 세션 id)와 원본 `merged_session_ids` 목록을 기록.
- `docs/merge_audit/chain_length_distribution.csv`: 체인 길이(몇 개 세션이
  합쳐졌는지) 분포. 대부분 2~3개(3,016개/759개)이고, 최대 15개까지 합쳐진
  경우도 1건 있음 (1~8단계 작업 당시 이미 확인한 분포와 동일).

## 3. 육안 확인용 샘플 (사람이 직접 검토)

- `docs/merge_audit/sample_merged_30.csv`: 병합 대상으로 판정된 사례
  무작위 30건. 간격(`gap_sec`), 종료~시작 GPS 거리(`gap_distance_m`),
  암시 속도(`implied_speed_mps`), 각 조각의 거리/시간
  (`prev_distance_km`/`prev_duration_sec`/`next_distance_km`/`next_duration_sec`)
  포함.
- `docs/merge_audit/sample_boundary_not_merged_30.csv`: 임계값 경계 근처
  (간격 150~210초 **그리고** 거리 150~250m)인데 병합되지 않은 사례. 전체
  연속 세션 쌍 113,571개 중 이 경계 조건을 만족하는 건 127개뿐이었고,
  그중 30건을 뽑았다 (나머지는 암시 속도 조건에서 걸렸을 수 있음 — 열
  `implied_speed_mps`로 직접 확인 가능).

## 4. Personalized history/hold-out 경계에 걸치는 체인

같은 운동의 조각(체인)이 사용자별 personalized 경계(history 80%/hold-out
20%)에 걸치는지 확인했다. personalized hold-out 샘플이 있는 사용자의
체인 4,109개 중 **29개**가 경계에 걸쳐 있다
(`docs/merge_audit/chains_straddling_personalized_boundary.csv`). 즉 이
29개 체인은 체인의 일부 조각은 history 쪽 세션이고 나머지 조각은 hold-out
쪽 세션이다 — 전체 체인의 0.7% 수준으로 드물지만 존재한다. 이번 감사에서는
"확인"만 요청되어 별도 보정은 하지 않았다 (추후 필요시 해당 체인이
걸린 사용자/윈도우를 personalized 평가에서 제외하는 보정을 검토할 수 있음).

## 5. 병합 전/후 비교 — 샘플을 (a)(b)(c)로 분리 (`15_merge_abc_breakdown.py`)

CLAUDE.md 경고대로 전체 평균만 비교하지 않고, 평가 샘플을 (a) 병합과
무관 (b) 입력(과거 5개) 세션이 병합 영향을 받음 (c) 타깃 세션 자체가
병합됨으로 나눠서 봤다. (과거 정보 감사(last_input_session_time)도
04/06단계와 동일하게 적용한 뒤의 수치다.)

| 평가방식 | 카테고리 | 샘플수(전) | MAE(전) | RMSE(전) | 샘플수(후) | MAE(후) | RMSE(후) |
|---|---|---|---|---|---|---|---|
| cold-start | (a) 무관 | 17,888 | 72.468 | 293.506 | 17,888 | 72.468 | 293.506 |
| cold-start | (b) 입력 영향 | 3,156 | 74.130 | 160.554 | 3,141 | 64.302 | 125.807 |
| cold-start | (c) 타깃 병합 | 2,556 | 86.509 | 266.400 | 967 | 59.522 | 100.962 |
| personalized | (a) 무관 | 17,470 | 63.823 | 258.657 | 17,420 | 63.802 | 258.601 |
| personalized | (b) 입력 영향 | 2,442 | 76.703 | 277.847 | 2,428 | 65.584 | 262.389 |
| personalized | (c) 타깃 병합 | 1,919 | 89.908 | 282.293 | 795 | 51.507 | 105.458 |

**핵심 관찰 (정정)**:
- **(a) 무관 그룹은 전/후 샘플 수와 MAE/RMSE가 거의 완전히 동일하다**
  (17,888/17,888, 72.468/72.468 등 — cold-start는 1비트도 안 바뀜,
  personalized는 소수점 차이만 있음(과거 정보 감사 제외 경계에 걸린
  극소수 때문)). 이는 "병합과 무관한 샘플은 정말로 영향을 안 받았다"는
  걸 검증하는 음성 대조군(negative control) 역할을 한다 — 비교 방법론이
  타당하다는 근거.
- **(b) 입력(과거 5개) 세션만 병합의 영향을 받고 타깃은 그대로인 그룹이
  정제 효과의 가장 깨끗한 증거다.** 이 그룹은 y(타깃의
  `avg_pace_sec_per_km`)의 정의가 전/후 동일하므로, MAE/RMSE 변화를
  "입력 품질이 좋아진 효과"로 해석할 수 있다. 실제로 MAE
  74.13→64.30(cold-start)/76.70→65.58(personalized), RMSE
  160.55→125.81/277.85→262.39로 개선되어, 쪼개진 조각을 병합해
  더 정확한 과거 입력을 주면 예측이 좋아진다는 것을 보여준다.
- **(c) 타깃 세션 자체가 병합된 그룹은 전/후를 직접 비교할 수 없다.**
  이 그룹은 병합으로 **y(정답)의 정의 자체가 바뀐다** — "병합 전"의 y는
  쪼개진 조각 하나의 페이스이고 "병합 후"의 y는 여러 조각을 합친 전체
  운동의 페이스라서, 서로 다른 타깃을 맞추는 다른 문제가 된다. 따라서
  RMSE가 266.4→101.0(cold-start), 282.3→105.5(personalized)로 줄어든
  것을 "정제 효과가 크다"고 해석하면 안 된다 — **입력 정제 효과와 정답
  정의 변화가 섞여 있어 분리할 수 없기 때문**이다 (샘플 수도
  2,556→967, 1,919→795로 줄어 타깃 인스턴스 자체가 재정의됐다는 점도
  같은 맥락). (c)는 "병합이 타깃 쪼개짐 문제를 줄인다"는 정성적 참고
  정보로만 쓰고, MAE/RMSE 개선폭을 정량적 근거로 인용하지 않는다.
- 종합하면, 전체 평균(기존 ablation, `09_merge_ablation.py`)에서 본
  "병합 후 MAE/RMSE가 전반적으로 개선된다"는 결과 중 **(b) 그룹에서
  확인된 개선만 입력 정제 효과로 확실히 귀속시킬 수 있고**, (c) 그룹의
  개선은 정답 정의 변화가 섞여 있어 같은 방식으로 해석할 수 없다.

## 6. 시간 겹침으로 제외된 2,700개 윈도우의 원인 분류 (`14_overlap_exclusion_audit.py`)

과거 정보 감사(04/06단계)에서 제외한 2,700개 윈도우를 다시 들여다봤다.

- 겹침 길이(`overlap_sec`): 중앙값 2,614초(약 44분), 최대 17,696초(약 4.9시간)
- 겹치는 쪽(마지막 과거 세션)의 거리/소요시간은 전체 세션 분포와 크게
  다르지 않음(평균 거리 8.0km, 평균 소요시간 3,030초) — 즉 "극단적으로
  긴 세션"만의 문제는 아니었다.
- **패턴 분류 (추정, 확정 아님)**:
  - **"같은 운동의 중복 기록으로 추정" (시작 시각 차이 ≤60초, 시작 좌표
    거리 ≤50m 둘 다 만족): 2,613건 (96.8%)** — 압도적 다수가 이 패턴에
    해당한다. 즉 애초 추정했던 "duration이 과도하게 긴 이상 세션" 때문이
    아니라, **같은 운동이 서로 다른 session_id로 중복 기록된 경우가
    대부분**이었던 것으로 보인다 (워치/앱이 겹쳐 기록하거나 재업로드된
    경우 등으로 추정).
  - "과거 세션 duration이 비정상적으로 길어 다음 세션을 덮음"으로 추정:
    33건 (1.2%)
  - 패턴에 들어맞지 않아 **미확인**: 54건 (2.0%)
  - 주의: 위 "중복 기록 추정"은 시작 시각/위치가 가깝다는 **간접 증거에
    기반한 추정**이며, 원본 데이터에 중복 업로드 여부를 알려주는 필드가
    없어 확정할 방법은 없다. "확인됨"이 아니라 "추정"으로만 표기한다.
  - 전체 목록: `docs/merge_audit/excluded_overlap_windows.csv`,
    육안 확인용 무작위 20건: `docs/merge_audit/excluded_windows_sample_20.csv`
- **특정 사용자에 집중**: 제외된 2,700건 중 사용자 1명(`user_id=7996903`)
  에서만 450건(16.7%)이 나왔다. 상위 10명 목록:
  `docs/merge_audit/excluded_windows_per_user.csv` 참고 (227명 중
  대다수는 소수 건이고, 일부 사용자에게 몰려 있음).

## 7. 시간이 겹치는 세션 쌍(간격이 음수)은 병합되지 않음 (확인)

전체 연속 세션 쌍 113,571개 중 간격이 음수(겹침)인 쌍은 2,747개였고,
그중 병합 대상으로 판정된 건 **0개**였다. `08_session_merge.py`의
`should_merge()`가 `gap_sec < 0 or gap_sec > MAX_GAP_SEC`일 때 바로
`False`를 반환하도록 되어 있어, 시간이 겹치는 쌍은 설계상 병합 대상이
아니다 — 코드와 실측 결과가 일치함을 확인했다 (`13_merge_audit.py`
실행 결과, `assert`로도 검증).

겹치는 쌍(2,747개)과 "시간 겹침으로 제외된 윈도우"(2,700개, 6번)는 서로
다른 집계 단위다 — 전자는 "모든 연속 세션 쌍" 기준, 후자는 "6세션 이상
사용자의 (과거5→타깃) 윈도우" 기준이라 숫자가 정확히 같지는 않지만
비슷한 규모로, 같은 근본 원인(겹치는 세션들)을 가리키고 있다.
