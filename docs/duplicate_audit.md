# 중복 기록 처리 (CLAUDE.md 10월 2주차 3-2번)

`docs/session_merge_audit.md`의 6번에서 발견한 "제외된 2,700개 윈도우 중
96.8%가 시작 시각·위치가 거의 동일한 중복 기록 패턴"을 근본적으로 처리한
작업 기록이다.

> **업데이트(최종 확정)**: 어느 쪽을 남길지 규칙은 **3단계
> (n_points desc → duration_sec desc → session_id asc)로 최종 확정**
> 했다 (3번 섹션 참고). start_time을 끼워넣는 4단계 버전과도 비교해봤고
> (3번 섹션), 영향은 무시할 수준임을 확인했다. 이 문서는 이제 최종
> 규칙 기준으로 갱신돼 있다.

## 1. 중복 판정 규칙 (사전 고정값, MAE로 조정하지 않음)

같은 사용자의 두 세션이 아래 세 조건을 **모두** 만족하면 중복으로 판정한다.
값은 `14_overlap_exclusion_audit.py`에서 이미 쓴 것과 동일하게 재사용했고,
이번에도 결과(MAE)를 보고 바꾸지 않았다.

| 조건 | 기준 |
|---|---|
| 시작 시각 차이 | ≤ 60초 |
| 시작 좌표 거리 | ≤ 50m |
| 시간 구간 겹침 | `max(start_A, start_B) < min(end_A, end_B)` |

전체 연속 쌍 중 **3,469쌍**이 이 조건을 만족했고, 서로 연쇄적으로 묶여
**2,128개 클러스터**(2개 이상이 중복 관계로 묶인 그룹)를 형성했다.
**2,687개 세션 제거** (111,738건 남음, 제거 전 114,425건).

## 2. 큰 차이가 있는 쌍 (육안 확인 결과)

20건 중 거리차 0.5km 초과 또는 시간차 300초 초과인 "큰 차이" 쌍이 있으면
`large_mismatch_flag` 열로 표시하도록 했다 (전체 2,687건 중 41건이 해당,
20건 샘플에는 그중 최대 3건을 섞어서 포함시켰다 — 무작위로만 뽑으면
이런 사례가 안 걸릴 수 있어서).

실제로 뽑힌 플래그 사례들을 보면 **전부 `overlap_ratio` ≈ 1.0(짧은 쪽
세션이 긴 쪽 세션의 시간 구간 안에 완전히 포함됨)이고 시작 좌표 거리도
2~34m로 매우 가깝다** — 즉 "거짓 양성"(중복이 아닌데 잘못 묶인 경우)으로
보이지는 않는다.

**원인은 "추정/미확인"으로만 표기한다.** "한쪽 기기/앱이 일찍 멈추거나
늦게까지 기록을 남겼다"는 그럴듯한 설명이지만, **원본 데이터에는 기기
종류·앱 종류를 알려주는 필드가 전혀 없다**(`docs/feature_availability.md`
확인 필드 11개 중 기기 관련 필드 없음 — 11개 전체가 speed/altitude/
gender/heart_rate/id/url/userId/timestamp/longitude/latitude/sport뿐).
따라서 "기기 차이"는 **검증 불가능한 추정**이고, "같은 운동의 중복
기록"이라는 것도 간접 증거(시작 시각·위치 근접, 시간 겹침)에 기반한
추정일 뿐 확정이 아니다. `user_id=10099521`의 cluster_size=4 클러스터에서
이 패턴이 반복된다는 것도 "관찰된 사실"이고, 그 원인이 무엇인지는
미확인이다.

## 3. 어느 쪽을 남길지 — tie-break 규칙 (최종 확정: 코드 기준 3단계)

**최종 규칙 (코드와 100% 일치, `16_duplicate_dedup.py`)**: **1순위
GPS 포인트 개수**(많은 쪽 유지) → **2순위(동률) duration_sec**(더 긴
쪽 유지) → **3순위(1·2순위 모두 동률) session_id**(작은 쪽). **start_time
단계는 없다.**

**왜 start_time이 아니라 duration인가**: 처음에는 2순위로 start_time
(빠른 쪽)을 썼다가, "의미" 기준으로 duration으로 바꿨다. 이유는 —
중복 쌍은 대부분 "같은 운동을 두 기록이 서로 다른 길이로 담아낸 경우"
이고(6번 참고), 우리가 진짜 알고 싶은 건 "어느 기록이 그 운동을 더
완전하게 담았는가"이다. **duration은 그 완전성을 직접 측정하는 값**
이고, start_time은 "어느 기록이 더 먼저 시작됐는가"일 뿐이라 **완전성을
간접적으로만 암시하는 지표**다 — 그래서 완전성을 직접 재는 duration을
2순위로 쓰는 쪽을 선택했다.

**이전 규칙(시작 시각 포함 4단계: n_points → start_time → duration →
session_id)과의 비교** (`22_dedup_tiebreak_4tier_experiment.py`, 실험만
수행, 프로덕션 파일은 영향 없음):

| 항목 | 값 |
|---|---|
| kept가 달라지는 클러스터 수 | **14 / 2,128 (0.66%)** |
| 제거 대상 session_id가 달라진 건수 | 28건 |
| 세션/자격 사용자/윈도우 수 변화 | **0** (전부 동일) |
| cold-start MAE/RMSE 변화 | **0.000000** (5개 baseline 전부, 소수점 6자리까지 동일) |
| personalized MAE/RMSE 변화 | -0.0007 ~ -0.0073 (MAE), -0.0005 ~ -0.0061 (RMSE) — 전부 무시 가능한 수준 |

**결론**: start_time 단계가 있든 없든 실질적인 차이는 거의 없다 —
위 비교는 "최종 규칙(3단계)이 성능을 해치지 않는다"는 부수적 확인일
뿐, 2순위를 duration으로 고른 이유 자체는 끝까지 "의미"(완전성을
직접 재는가)였다.

**예전 코드의 비결정성 버그(참고, 이미 고쳐짐)**: 맨 처음 작성했던
버전은 3순위(session_id)가 없어서, 1·2순위가 모두 동률일 때 Python
`set`의 내부(해시 기반) 순회 순서로 결정되는 **비결정적 코드**였다.
session_id를 3순위로 추가해 항상 같은 결과가 나오도록 고쳤다.

**"어느 쪽을 남겨도 통계적으로 차이 없다"는 주장의 근거 (최종 규칙
기준으로 재확인)**: 최종 규칙에서 1·2순위(포인트 수, duration_sec)가
모두 동률인 쌍은 **2,687건 중 2,235건(83.2%)**이다. duration이
동률이라는 정의상 이 그룹의 `duration_diff_sec`는 전부 0이고, 남는
변수는 거리뿐이다.

| 지표 | 중앙값 | 95백분위 | 최댓값 |
|---|---|---|---|
| 거리 차이(km) | **0.000** | 0.023 | 0.859 |
| 시간 차이(초) | **0.000**(정의상 전부 0) | 0 | 0 |

이 동률 그룹(2,235건)에서는 최댓값조차 0.86km로 작고, `large_mismatch_flag`
(거리차 0.5km 초과 또는 시간차 300초 초과)에 걸리는 건 **1건뿐(0.04%)**
이다 — 구버전(start_time 2순위) 분석 때보다(2,268건 중 5건, 최댓값
12.88km) 훨씬 깨끗하다. 즉 "통계적으로 차이 없음"은 이 최종 규칙의
동률 그룹에서는 **거의 전부(99.96%)에 대해 성립**하고, 극소수
이상값에는 적용되지 않는다 — 이 1건에 대해서는 어느 쪽이 남는지가
실제로 결과에 영향을 줄 수 있으므로 "차이 없음"을 전체에 대해 단정하지
않는다.

## 5. 3개 이상 묶인 중복 클러스터

2,128개 클러스터 중 **392개(18.4%)가 3개 이상의 세션으로 묶인
클러스터**였다 (총 1,343개 세션 포함, 클러스터당 평균 3.4개). 즉 같은
운동이 2번뿐 아니라 3번, 많게는 더 여러 번 중복 기록된 경우가 드물지
않게 있었다.

**클러스터 처리 방식 (코드 기준)**: `find_duplicate_pairs()`가 찾은
직접 쌍들을 **union-find로 전이적으로(transitively) 연결**한다 — A-B가
직접 조건을 만족하고 B-C가 직접 조건을 만족하면, A-C가 직접 조건을
만족하는지는 검사하지 않고도 A/B/C를 하나의 클러스터로 묶는다. 그 다음
클러스터 안에서 tie-break 규칙(포인트 수 → start_time → session_id)
으로 **1개만 남기고 나머지는 전부 제거**한다 (쌍별로 따로 처리하지
않음).

**전이적 연결의 위험성 검증**: 이 방식은 이론적으로 "A-C는 직접
조건을 만족하지 않는데 B를 거쳐 전이적으로만 묶인" 경우를 만들 수
있다. 392개의 3개 이상 클러스터에 대해 **모든 쌍 조합(C(n,2), 총
1,733쌍)을 직접 재검사**한 결과, **조건을 만족하지 않는 쌍은 0건
이었다** — 즉 이 데이터셋에서는 모든 3중 이상 클러스터의 구성원들이
실제로 서로 쌍쌍이(pairwise) 조건을 만족했고, 전이적 연결로만 묶인
"가짜 클러스터"는 발견되지 않았다. (코드 구조상 이런 위험이 원천적으로
배제된 것은 아니며, 이번 데이터에서 우연히 발생하지 않았을 뿐이라는
점은 분명히 해둔다.)

## 7. 처리 순서: 중복 제거를 병합보다 먼저 (이유 — 실측으로 확인됨)

중복 기록(같은 운동이 두 번 찍힘)과 병합 대상(한 운동이 여러 조각으로
쪼개짐)은 서로 다른 현상이라, 중복을 먼저 치우지 않으면 병합 로직이
"쪼개진 진짜 다음 조각"과 "중복 사본" 중 하나를 잘못 체인으로 묶을
위험이 있다고 판단해 (1) 중복 제거 → (2) 병합 순서로 처리했다.

아래 8번의 단계별 표를 보면 이 순서가 왜 중요한지 실측으로도 확인된다:
**병합만 적용(중복 제거 없음)으로는 과거 정보 감사 제외 건수가 거의
줄지 않는다** (cold-start 745→734, personalized 2,700→2,676 — 거의
그대로). 이는 08단계의 병합 규칙이 `gap_sec < 0`(시간이 겹치는 쌍)을
애초에 병합 대상에서 제외하도록 설계되어 있어서다 (`13_merge_audit.py`
7번에서 이미 확인한 내용) — 즉 **병합은 중복 문제를 전혀 해결하지
못한다.** 반대로 **중복 제거만 적용(병합 없음)으로는 제외 건수가 이미
97% 이상 줄어든다** (745→19, 2,700→93). 병합은 그 다음에 남아있는
"진짜로 쪼개진 조각" 문제를 추가로 줄여준다 (19→8, 93→69). 이 둘은
서로 다른 문제를 해결하는 보완적인 단계라는 것이 이번 감사로 분명해졌다.

## 8. 단계별 건수표: 원본 run → dedup 후 → 병합 후

**단위 명시**: "세션수"는 세션(러닝 1회 기록) 단위, "윈도우"는
(과거 5개 세션 → 타깃 1개) 평가 샘플 단위다. "제외"는 **윈도우 단위**로
과거 정보 감사(`last_input_session_time >= target_start_time`)에 걸려
해당 평가 조건(cold-start 또는 personalized)의 데이터셋에서 빠진
윈도우 수다. cold-start와 personalized는 서로 다른 사용자/세션 부분
집합을 평가하므로 같은 단계에서도 두 숫자가 다르다 (cold-start는
test_user_ids 150명 전후만, personalized는 전체 자격 사용자의 hold-out
구간만 평가).

| 단계 | 세션수 | 병합체인수 | 병합으로<br>줄어든 세션수 | 사용자수 | cold-start<br>윈도우 | cold-start<br>제외(윈도우) | personalized<br>윈도우 | personalized<br>제외(윈도우) |
|---|---|---|---|---|---|---|---|---|
| 0. 원본 run (정제 없음) | 114,425 | 0 | 0 | 748 | 23,600 | 745 | 21,831 | 2,700 |
| 1. dedup 후 (병합 전) | 111,738 | 0 | 0 | 745 | 23,583 | **19** | 21,817 | **93** |
| 2a. 병합만 (dedup 없음) | 108,392 | 4,109 | 6,033 (114,425→108,392) | 745 | 21,996 | 734 | 20,643 | 2,676 |
| 2b. dedup→병합 (최종) | 105,709 | 4,072 | 6,029 (111,738→105,709) | 742 | 21,978 | **8** | 20,629 | **69** |

**"745→19" 등 수치의 대응 관계 (이전 보고와 일치 확인)**:
- **cold-start, 윈도우 단위**: 0단계(원본) 745 → 1단계(dedup만) **19**
  → 2a단계(병합만) 734 → 2b단계(최종) **8**
- **personalized, 윈도우 단위**: 0단계(원본) 2,700 → 1단계(dedup만)
  **93** → 2a단계(병합만) 2,676 → 2b단계(최종) **69**

이전 채팅 보고에서 "8/69"라고 썼던 수치는 **이 표의 2b(최종) 행의
cold-start/personalized 제외 건수**를 가리킨 것이고, "745→19"는 **0단계
→ 1단계(dedup만 적용, 병합 전) 구간의 cold-start 제외 건수 변화**를
가리킨 것이다 — 서로 다른 두 단계 쌍을 비교한 숫자라 혼동하기 쉬워
이 표로 명확히 했다.

(1행과 2a행을 비교하면 "병합만으로는 거의 효과 없음(745→734,
2,700→2,676), dedup만으로 97% 이상 해소(745→19, 2,700→93)"가 숫자로
드러난다.)
