# 원자료 → 5km 시간(T5) 추적표

생성: `scripts/59_source_trace.py`(저장소 루트에서 `python scripts/59_source_trace.py --zip <저장소 밖 폴더>/health.zip`; 원본 `endomondoHR.json`과 `data/` 필요). 새 분석이 아니라 기존 계산(`01_parse_run_sessions.py`의 haversine·스킵 규칙, `38_build_5km_dataset.py:compute_t5`, `demo/import_apple_health.py`)을 단계별로 풀어 보인 것이다. 결과 숫자·정의·모형·범위는 바꾸지 않았다. 연구 데이터는 "academic use only, 재배포 금지"라 세션 ID·사용자 ID·좌표·원본 값 목록은 싣지 않고 사례 이름(F1·F2)과 집계값만 적는다. 내 애플워치 기록은 저장소 밖 자료라 사례 A·B·C로만 적었고 날짜·좌표·심박 값은 뺐다(시각은 숫자를 가린 형식 패턴만 적음). 시각은 start_time 원값(기준 미확인)이며 모든 T5는 "정지 시간 포함(경과 시간 기준)"이다.

## 1. 사례 선정 규칙

- FitRec 원자료의 키(좌표 제외): altitude, gender, heart_rate, id, sport, timestamp, url, userId. 거리·경과 시간 필드는 없다.
- 사례 F1·F2(FitRec): 후보(비병합 세션, 5.0~5.5km, T5 ≤ 5,000초)이면서 T5 캐시에 있는 세션 5,380개 중 F1 = session_id가 가장 작은 것, F2 = 경과−이동 시간 비율(`gap_ratio`)이 가장 큰 것(정지·공백 처리 대조용). 사람이 고른 것이 아니라 규칙으로 정했다.
- 사례 S1·S2(합성 GPX): `demo/test_import_apple_health.py`의 합성 GPX 생성기. S1 = 균일 100m/30초로 60점(59구간), S2 = 제자리 점 10개 뒤 같은 속도로 70점. 합성 Workout(거리 5.9km·6.0km, 종료−시작 = 점 시각)과 함께 가져오기 코드를 그대로 통과시켰다.
- 사례 A·B·C(내 애플워치 기록): 건강 내보내기 ZIP의 달리기 중 5.0~5.5km·경로 있음·경로 거리 5km 이상인 10개에서 A = 가장 이른 것, B = `stop_sec` 최대, C = 가장 늦은 것(겹치면 다음 순위).

## 4. 확인된 차이 / 미확인

원인은 추정하지 않는다. 숫자로 확인된 것만 "확인된 차이"에 적고, 이 자료로 알 수 없는 것은 "미확인"에 적는다.

### 미확인
- FitRec 시각(정수 에포크 초)의 시간대 기준(UTC 여부)은 판정할 수 없다(`docs/week4_data_audit.md`). T5는 같은 세션 안 시각 차이라 시간대와 무관하지만, `start_time`을 달력 날짜로 읽는 용도(월요일 격자)는 가정이다.
- FitRec 원자료의 점 기록 규칙(샘플링 주기, 일시정지 중 점이 기록되는지)과 일시정지 이벤트는 원자료에 없어 알 수 없다. 위 표의 "간격 60초 초과"는 점 시각 간격만 보여 줄 뿐 일시정지인지는 구분하지 못한다.
- 애플 Workout 거리 통계가 어떤 센서·알고리즘으로 계산되는지, GPX 경로 거리와의 차이의 원인은 이 자료로 알 수 없다. 위 차이는 이 사례들에서 관측된 값일 뿐이며 다른 기록으로 일반화하지 않는다.
- 애플 GPX 점 간격 규칙과, 일시정지 구간이 GPX에서 점 간격으로 남는지(또는 점이 비는지)는 이 사례들에서 관측된 것만 적었다. 기기·운영체제 버전별 동작은 미확인이다.
- 가져오기 CSV의 `start_time`·`end_time`은 Workout 시각의 시간대 표기(예: +0900)를 떼고 현지 벽시계 값으로 적는다(변환하지 않음). GPX `<time>`은 UTC(Z)라 같은 순간이 두 표기로 달라 보일 수 있으나, T5·`stop_sec`는 GPX 안 시각 차이만 쓰므로 영향이 없다. `--asof`는 CSV와 같은 벽시계 기준으로 지정해야 한다.
